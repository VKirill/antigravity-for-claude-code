### 1. Дыра в проверке AST-линтера: почему «нейрожижа» легко попадет в прод?
В файле [craft-gate.mjs](file:///home/ubuntu/.gemini/antigravity-cli/scratch/scripts/craft-gate.mjs) первый проход валидации исходного кода реализован так:
```javascript
const cssFiles = globSync('src/**/*.css');
```
* **Каверзный вопрос:** Почему проверка на запрещенные цветовые форматы (Hex/RGB/HSL), обязательное использование OKLCH и функции `clamp()` выполняется **только** для файлов `.css`?
* **Суть проблемы:** Astro по умолчанию поощряет написание стилей непосредственно внутри компонентов в блоках `<style>` (Scoped Styles). Если агент-разработчик напишет грязный CSS с плоскими цветами (например, `#ff0000`) прямо в [HeroSection.astro](file:///home/ubuntu/.gemini/antigravity-cli/scratch/src/components/HeroSection.astro), первый проход линтера этот файл **вообще проигнорирует**.
* **Следствие:** Второй проход (`checkBundleOutput`) проверяет собранный бандл в `dist/` только на «позитивные» признаки (наличие CSS Grid, анимаций и `@media (prefers-reduced-motion)`), но он **не ищет запрещенные Hex-цвета или отсутствие clamp в бандле**. В итоге некачественный код без проблем пройдет валидацию.

### 2. Иллюзия автоматизации «Human Image Gate»
В спецификации [art-direction-forcing.md](file:///home/ubuntu/.gemini/antigravity-cli/scratch/art-direction-forcing.md) описан шаг, где пайплайн останавливается и ждет одобрения сгенерированного макета:
```bash
# Команда, запускаемая агентом для создания концепта UI
generate_image --Prompt "..." --ImageName "ui_mockup_concept"
```
* **Каверзный вопрос:** Каким образом изолированный headless-скрипт оркестратора [run-pipeline.js](file:///home/ubuntu/.gemini/antigravity-cli/scratch/scripts/run-pipeline.js), работающий на уровне ОС, может «заставить» LLM-агента вызвать MCP-инструмент `generate_image`?
* **Суть проблемы:** Оркестратор запускает дочерние процессы через `execSync`. Процесс Node.js не имеет обратной связи с контекстом LLM, чтобы скомандовать «вызови свой инструмент генерации картинок». Пайплайн просто запишет статус `WAITING_FOR_APPROVAL` и завершит работу. Логика интеграции «человеческого гейта» и генерации концепта разорвана и требует ручного вмешательства, что рушит концепцию непрерывного закрытого цикла.

### 3. Хаос с путями и именами файлов `tokens.css`
Существует явное противоречие между базой данных задач, пайплайном и самими скриптами валидации.
* **В базе данных** (описано в [pipeline-enforcement.md](file:///home/ubuntu/.gemini/antigravity-cli/scratch/pipeline-enforcement.md)):
  Ожидается создание артефакта `src/styles/tokens.css`, который проверяется через `node oklch-color-system/verify-contrast.js`.
* **Внутри скрипта** [verify-contrast.js](file:///home/ubuntu/.gemini/antigravity-cli/scratch/oklch-color-system/verify-contrast.js#L29):
Написано жестко захардкоженное чтение из текущей директории:
  ```javascript
  const css = fs.readFileSync('tokens.css', 'utf-8');
  ```
* **В корневой директории** лежит еще один файл [verify_contrast_ci.js](file:///home/ubuntu/.gemini/antigravity-cli/scratch/verify_contrast_ci.js#L191), который делает:
  ```javascript
  const cssFilePath = path.join(__dirname, 'tokens.css');
  ```
* **Каверзный вопрос:** Какой именно файл в итоге валидируется? Тот, что лежит в корне, или тот, что лежит в `src/styles/`? Если оркестратор запускает валидатор из корня репозитория, он может проверять устаревший шаблонный `tokens.css`, полностью игнорируя сгенерированный агентом артефакт в `src/styles/`.

### 4. Крайне хрупкий regex-парсинг CSS-переменных
Скрипты валидации используют жесткие регулярные выражения для извлечения токенов. Например, в [verify-contrast.js](file:///home/ubuntu/.gemini/antigravity-cli/scratch/oklch-color-system/verify-contrast.js#L35):
```javascript
const colorRegex = /^\s*(--color-[a-z0-9-]+):\s*oklch\(([\d\.]+)\s+([\d\.]+)\s+([\d\.]+)\);/gm;
```
* **Каверзный вопрос:** Что произойдет, если агент сгенерирует вполне валидные по спецификации CSS переменные, но запишет их в формате `--blue-50` (без префикса `--color-`), или добавит запятые в `oklch()`, или объявит их с использованием fallback-значений вроде `var(--primary, oklch(...))`?
* **Суть проблемы:** Валидатор упадет с ошибкой парсинга, хотя CSS будет абсолютно рабочим. Использование регулярных выражений вместо полноценного CSS-парсера (например, PostCSS) для семантического анализа делает билд-систему избыточно капризной и склонной к ложноположительным отказам.

---

### 5. Деструктивный и опасный откат (`git reset --hard`)
Оркестратор при любой ошибке валидации выполняет откат изменений:
```javascript
rollbackToCheckpoint(commitSha); // git reset --hard
```
* **Каверзный вопрос:** Как эта система будет работать в многопользовательской среде или при наличии параллельно работающих суб-агентов?
* **Суть проблемы:** `git reset --hard` — это ядерное оружие. Если во время работы агента изменились локальные служебные файлы (например, логи оркестратора, кэш, файлы состояния БД или другие ветки разработки), жесткий откат уничтожит всю историю работы без возможности восстановления. Кроме того, при падении теста из-за внешнего фактора (таймаут сети, сбой окружения) агент теряет весь написанный код, и ему приходится начинать генерацию с нуля, что неэффективно расходует токены.

### 6. Геймификация доступности (A11y): почему баллами можно «откупиться» от ошибок?
В спецификации [craft-gate-full.md](file:///home/ubuntu/.gemini/antigravity-cli/scratch/craft-gate-full.md) установлена планка прохождения в 80 баллов.
* **Каверзный вопрос:** Почему отсутствие важнейшей медиа-функции доступности `@media(prefers-reduced-motion)` (которая должна блокировать мерцания для людей с вестибулярными расстройствами) просто снимает 15 баллов, но позволяет проекту пройти валидацию?
* **Суть проблемы:** Если проект наберет 85 баллов за счет использования OKLCH, CSS Grid и 13 уникальных токенов, драфт-гейт вернет `exit code 0`, проигнорировав отсутствие доступности и анимационных заглушек. Делать фундаментальные правила доступности (Accessibility) опциональными баллами в геймифицированном скоринге — грубая методологическая ошибка.

### 1. Нейрошлак никуда не денется, он просто перекрасится в OKLCH
Вы наивно полагаете, что зажав вероятностную языковую модель в тиски жестких правил PostCSS AST-линтера (`craft-lint.js`), вы заставите ее генерировать «премиальный дизайн». Какая глупость! 
Модель не обладает вкусом. Она не начнет «творить искусство» от того, что вы бьете ее палкой линтера. Она просто научится хакать ваши правила:
* Ей нужен `oklch()`? Она сгенерирует абсолютно несочетаемые, вырвиглазные цвета, но строго в формате `oklch()`.
* Нужен `clamp()`? Она напишет бессмысленные формулы адаптивности, от которых верстка поползет на первом же нестандартном экране.
* Нужен CSS Grid? Она обернет все элементы в бессмысленные сетки, превратив DOM-дерево в лабиринт.
На выходе вы получите тот же самый «нейрошлак» (flat neuroslop), только более дорогой, переусложненный и абсолютно не поддерживаемый. Вы просто автоматизировали производство мусора, проходящего тесты.

### 2. Финансовый пылесос и бесконечный цикл откатов
Ваша гениальная идея с `git rollback` при любой ошибке валидации — это прямой путь в долговую яму к провайдерам LLM.
Представьте реальный процесс:
1. Агент сгенерировал код.
2. Линтер завершился с ошибкой (например, контрастность текста на 0.1 Lc ниже нормы).
3. Оркестратор делает жесткий откат (`git checkout .`).
4. Оркестратор снова шлет дорогой запрос к API с логами ошибок.
5. Агент пытается исправить, но ломает другое правило (например, забывает `clamp()`).
6. Снова откат. Снова запрос.
Ваши лимиты API сгорят за 10 минут, а счет за токены превысит годовую зарплату нормального фронтенд-разработчика. И всё это ради того, чтобы сверстать несчастную Hero-секцию на Astro с анимацией на GSAP? Вы серьезно?

### 3. Привет от призраков прошлого (The Grid и автоматический UX)
Вы думаете, что вы первые, кто пытается сделать «автоматический идеальный дизайн»? 
* Вспомните легендарный стартап **The Grid** (2014-2016 гг.). Они собрали миллионы долларов, обещая сайты, которые «сами себя проектируют на основе ИИ». В итоге они выдали неюзабельный, тормозящий визуальный мусор и закрылись под улюлюканье обманутых инвесторов.
* Посмотрите на мучения Wix ADI или Bookmark. Алгоритмический дизайн всегда выглядит либо как безликий шаблон из 2010 года, либо как генеративный кошмар сумасшедшего.
* В реальной разработке слишком жесткие линтеры в CI всегда приводят к одному: люди пишут `/* eslint-disable */` или лепят костыли-заглушки (dummy variables), чтобы просто билд прошел. Ваш ИИ сделает ровно то же самое — он найдет лазейку в регулярках линтера и просунет туда свой некачественный код.

### 4. Архитектурный Франкенштейн на костылях
Посмотрите на ваш стек: SQLite для отслеживания DAG-шагов, шелл-скрипты, PostCSS AST-парсеры, Zod-схемы, Playwright для скриншотов... Всё это связано синей изолентой и работает только в стерильных условиях.
* Что произойдет, когда обновится `postcss`? Или когда OpenAI/Anthropic выпустят обновление модели, изменив ее дефолтный формат вывода?
* Что будет, когда в SQLite запишется битый стейт из-за прерванного процесса?
Ваша система требует тонны поддержки. Вы тратите 90% времени не на создание сайтов, а на написание валидаторов для валидаторов. Это классический пример «проблемы второго порядка» — когда борьба с инструментами разработки важнее самой разработки.
