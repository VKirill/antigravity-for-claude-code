# Чек дебатов (Debate Receipt)

### 1. Тема обсуждения
Обсуждение было посвящено двум взаимосвязанным архитектурным вопросам:
1. **Миграция среднеразмерного e-commerce проекта с Next.js Pages Router на App Router (Next.js 16)** для оптимизации ключевых метрик Core Web Vitals (в первую очередь LCP и INP). Рассматривалось использование преимуществ React Server Components (RSC), Partial Prerendering (PPR), новой директивы `'use cache'` и Server Actions.
2. **Внедрение автоматического проверочного контура качества (Site-Harness Pipeline)** для предотвращения генерации «нейрошлака» (шаблонных, визуально скучных и некачественных интерфейсов, создаваемых большими языковыми моделями). Обсуждалась строгость проверок на уровне AST-анализа исходного кода, аудит собранного бандла, автоматические откаты изменений в Git при сбоях и использование локальной базы данных для управления фазами пайплайна.

### 3. Отвергнутые альтернативы
В ходе обсуждения были предложены и отклонены следующие варианты решений:

1. **Полный отказ от автоматических проверок кода в пользу ручного визуального контроля (предложение Соглашателя):**
* *Причина отклонения:* Без жестких автоматизированных проверок языковые модели неизбежно скатываются к генерации плоских, шаблонных макетов и игнорируют требования к качеству кода, стилю и доступности.
2. **Полный отказ от идеи создания проверочного контура качества (позиция Хейтера):**
* *Причина отклонения:* В e-commerce проекте критически важно поддерживать строгие визуальные стандарты; отказ от автоматизации проверки приведет к быстрой деградации кодовой базы.
3. **Жесткий откат изменений (`git reset --hard`) при первой же ошибке валидации:**
* *Причина отклонения:* Этот подход уничтожал до 95% корректно выполненной работы агента из-за мелкой опечатки, приводил к потере локальных данных и мешал параллельной работе над другими задачами.
4. **Проведение всех проверок исключительно на уровне собранного бандла (`dist/`):**
* *Причина отклонения:* Оптимизаторы и сборщики (PostCSS/Vite) сжимают код и транспилируют современные свойства (например, переводят `oklch` обратно в HEX/RGB для совместимости со старыми браузерами), что приводило к ложным срабатываниям линтера.
5. **Замена базы данных SQLite на плоский файл состояния `.harness/state.json`:**
* *Причина отклонения:* Для надежной оркестрации фаз выполнения и предотвращения конфликтов в многопоточном режиме необходима транзакционность, которую плоский файл состояния обеспечить не может.

### 4. Итоговое принятое решение
На основе компромиссов, предложенных Синтезатором (ведущим архитектором), утверждено следующее решение:

1. **Поэтапная миграция на Next.js 16 App Router одобрена:** Переход будет реализован в 5 фаз (от простых статических страниц до корзины и чекаута с поэтапным внедрением PPR, Server Actions и `'use cache'`).
2. **Модернизация контура проверок (Quality Harness):**
   * **Переход на мягкие гейты (Soft Gates):** Вместо немедленного жесткого отката изменений агент получает до 3 попыток исправить код прямо на месте (in-place) на основе логов ошибок компилятора или линтера.
* **Двухпроходной аудит (Dual-Pass Audit):** Проверка разделена на два шага:
- *Pass 1 (AST-анализ на уровне исходного кода в `src/`):* Контроль использования OKLCH-цветов, fluid clamp и дизайн-токенов.
- *Pass 2 (Аудит собранного бандла в `dist/`):* Проверка наличия CSS Grid, импорта GSAP, анимаций и поддержки `prefers-reduced-motion`.
* **Борьба с «театром соответствия»:** Внедряется визуальное тестирование (Playwright + Screenshot Diff) для проверки реального рендеринга страницы вместо слепого поиска подстрок в коде.
* **Изоляция рабочих пространств:** Для параллельной работы агентов будут использоваться изолированные `git worktrees` или контейнеры, что исключает конфликты глобальных откатов.
* **Визуальные гейты (Human Concept Gates):** Сложные дизайн-фазы (например, `art-direction`) блокируются до ручного одобрения человеком сгенерированных ИИ макетов (фреймов), предотвращая написание кода под неверную концепцию.
   * **Оптимизация БД:** База SQLite переведена в режим WAL (Write-Ahead Logging) для предотвращения взаимных блокировок.
