## What "good" looks like in 30 seconds

A passing skill has:
- Description 150–400 chars with trigger terms + "use when" phrasing
- SKILL.md body sections in this order: Usage → Use this skill when → Do not use → Purpose → Capabilities (with bodies) → Behavioral Traits → Important Constraints → Related Skills → API Reference
- references/ directory (if any) where every file is linked from SKILL.md and every file is < 500 lines
- Version block (if version-sensitive) generated by `sync_skill_versions.py`
- No placeholder section bodies, no time-sensitive prose, no broken `[references/...](references/...)` links

## How Claude actually picks a skill

When a user message arrives, Claude scans active skill descriptions for routing signals. Descriptions that **list the concrete words a user would say** win. Generic "Master Python with modern features" loses to "Use when: writing Python 3.14+ code, fixing async bugs, configuring uv, running pytest, optimizing with free-threaded build".

This is why the `description` field deserves more design time than the body. Most skill body fixes don't help routing — they only help once the skill is loaded.
