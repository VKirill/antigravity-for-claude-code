# Alembic migrations

Alembic is the migration tool packaged with SQLAlchemy. It stores a versioned chain of migration scripts, supports autogenerate from your `MetaData`, and handles both sync and async engines.

## Install and initialize

```bash
uv add alembic
```

Initialize one of three layouts:

```bash
alembic init alembic                  # generic — sync
alembic init -t async alembic         # async — env.py uses async_engine
alembic init -t multidb alembic       # one repo, multiple databases
```

This creates:

```
alembic/
├── env.py              # the bootstrap — wire your metadata here
├── script.py.mako      # template for new migration files
├── versions/           # generated migration scripts
└── README
alembic.ini             # config (db URL, logging, file paths)
```

## `alembic.ini` — the parts that matter

```ini
[alembic]
script_location = alembic
sqlalchemy.url = postgresql+psycopg://user:pass@localhost/mydb
# Or load from env: keep this empty, set it from env.py via os.environ.

# Format the generated revision filename with a timestamp
file_template = %%(year)d_%%(month).2d_%%(day).2d_%%(hour).2d%%(minute).2d-%%(rev)s_%%(slug)s

[post_write_hooks]
hooks = ruff_format
ruff_format.type = console_scripts
ruff_format.entrypoint = ruff
ruff_format.options = format REVISION_SCRIPT_FILENAME
```

For production, load the URL from env in `env.py` and leave `sqlalchemy.url` empty in `alembic.ini`:

```python
# env.py
import os
config = context.config
config.set_main_option("sqlalchemy.url", os.environ["DATABASE_URL"])
```

## `env.py` — sync template

The canonical sync template (paraphrased; check your generated file):

```python
from logging.config import fileConfig
from sqlalchemy import engine_from_config, pool
from alembic import context

# import your Base.metadata
from app.models import Base

config = context.config
if config.config_file_name is not None:
    fileConfig(config.config_file_name)

target_metadata = Base.metadata


def run_migrations_offline() -> None:
    url = config.get_main_option("sqlalchemy.url")
    context.configure(
        url=url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
    )
    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(connection=connection, target_metadata=target_metadata)
        with context.begin_transaction():
            context.run_migrations()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

`poolclass=NullPool` is important — migrations shouldn't reuse pooled connections.

## `env.py` — async template

```python
import asyncio
from logging.config import fileConfig
from sqlalchemy import pool
from sqlalchemy.ext.asyncio import async_engine_from_config
from alembic import context

from app.models import Base

config = context.config
if config.config_file_name is not None:
    fileConfig(config.config_file_name)

target_metadata = Base.metadata


def do_run_migrations(connection):
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        context.run_migrations()


async def run_async_migrations():
    connectable = async_engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)
    await connectable.dispose()


def run_migrations_online():
    asyncio.run(run_async_migrations())


if context.is_offline_mode():
    # offline mode uses the sync flow even for async URLs
    url = config.get_main_option("sqlalchemy.url")
    context.configure(url=url, target_metadata=target_metadata, literal_binds=True)
    with context.begin_transaction():
        context.run_migrations()
else:
    run_migrations_online()
```

The trick: `connection.run_sync(do_run_migrations)` lets Alembic's sync machinery operate on a sync proxy of the async connection.

## Naming convention — set this BEFORE the first migration

Without naming conventions, autogenerated constraints get implementation-defined names (e.g., `users_email_key`). They're stable enough until you try to rename or drop them — then Alembic can't find them.

Set this on your `MetaData` before any tables are declared:

```python
from sqlalchemy import MetaData
from sqlalchemy.orm import DeclarativeBase

NAMING_CONVENTION = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}


class Base(DeclarativeBase):
    metadata = MetaData(naming_convention=NAMING_CONVENTION)
```

Adding this AFTER you already have a populated DB requires manual ALTER ... RENAME CONSTRAINT for every existing constraint. Set it on day one. See [recommended-defaults.md](recommended-defaults.md).

## Autogenerate workflow

```bash
alembic revision --autogenerate -m "add users.full_name"
# inspect the generated file in alembic/versions/
alembic upgrade head
```

Always inspect the diff. Autogenerate **reliably** detects:

- Tables added/removed
- Columns added/removed
- Nullability changes
- Index and unique constraint changes (named)
- Foreign key changes

Autogenerate **does not** detect:

- Column renames (you'll see a drop + add — manually edit to `op.alter_column(..., new_column_name=...)`)
- Table renames (same — manually edit)
- Anonymously named constraints
- Some server-default changes (enable `compare_server_default=True` for partial help)
- Enum value changes on Postgres `ENUM` types
- `CHECK` constraint edits

For these, write the migration by hand or edit the autogenerated draft.

## Tightening autogenerate

In `env.py`:

```python
context.configure(
    connection=connection,
    target_metadata=target_metadata,
    compare_type=True,
    compare_server_default=True,
    include_schemas=True,            # if you use multiple schemas
    render_as_batch=False,           # set True for SQLite ALTER COLUMN support
)
```

`compare_type=True` is the default since Alembic 1.12 but worth being explicit.

## Multiple metadatas (multi-base)

```python
target_metadata = [PublicBase.metadata, AnalyticsBase.metadata]
```

Used when you have multiple `DeclarativeBase` subclasses for isolated schemas in the same DB.

For truly separate databases, use `alembic init -t multidb` and the per-database section pattern in `alembic.ini`.

## Data migrations

Schema changes that also rewrite data:

```python
def upgrade() -> None:
    op.add_column("users", sa.Column("display_name", sa.String(120), nullable=True))

    bind = op.get_bind()
    users_t = sa.table(
        "users",
        sa.column("id", sa.Integer),
        sa.column("full_name", sa.String),
        sa.column("display_name", sa.String),
    )
    bind.execute(
        sa.update(users_t).values(display_name=users_t.c.full_name)
    )

    op.alter_column("users", "display_name", nullable=False)


def downgrade() -> None:
    op.drop_column("users", "display_name")
```

Notes:

- Don't import your ORM models inside `env.py` migration scripts — the models evolve, but old migrations need to keep using the schema as it was at that point. Use lightweight `sa.table(...)` + `sa.column(...)` references.
- For large tables, do schema + data in **separate migrations** and split the steps: add nullable column → backfill in batches outside migration → set NOT NULL.
- Idempotent migrations (re-runnable on partial failure) are worth the effort for big tables.

## Downgrade safety

Most teams enable `alembic downgrade -1` only for dev. For production:

- Test downgrade in staging before every release.
- Destructive downgrades (column drops, data loss) → leave the `downgrade()` empty with a `raise NotImplementedError("data-destructive — restore from backup")` if a real rollback isn't possible. Better to make it explicit than silently delete data.

## CI gate — `alembic check` (recent versions)

```bash
alembic check
```

Returns non-zero if models drifted from migration history. Run it in CI on every PR — catches "forgot to autogenerate" before merge.

## Common commands

```bash
alembic current                            # show current revision
alembic history                            # show full chain
alembic upgrade head                       # apply all pending
alembic upgrade +1                         # apply next one
alembic downgrade -1                       # back off one
alembic upgrade ae1027a6acf                # to specific rev
alembic revision -m "add foo"              # blank migration
alembic revision --autogenerate -m "..."   # auto from metadata diff
alembic stamp head                         # mark DB as "at head" without running
```

`stamp` is the escape hatch when you've created the schema by other means (e.g., restored from a dump) and just need Alembic to know where it is.
